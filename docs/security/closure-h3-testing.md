# H3 boot-closure VM test

`tests/vm/closure_boot.py` exercises boot-time fail-closed behavior in the disposable QEMU guest created by `tests/vm/run.py`. The host runner owns QEMU, the SSH key, reboot boundaries, and the external host-forward probe. The guest helper never selects a Docker remote: it requires `DOCKER_HOST` to be unset, a root-owned `0600` `/run/l4d2-suite-vm.json` marker declaring `{"virtualization":"qemu","disposable":true}`, QEMU/KVM virtualization, systemd as PID 1, and the trusted suite under `/opt/l4d2-firewall`.

The runner installs the three production firewall units from `systemd/` before invoking the helper. The helper compares those installed files byte-for-byte with the trusted templates. It creates only uniquely named H3 fixtures, refuses to replace existing unit, Docker, nftables-sentinel, or state paths, and records the original transaction files and firewall configuration file metadata for exact cleanup checks.

The host runner invokes the following guest phases in order, with external probes and reboots between selected calls:

| Phase | What it proves |
| --- | --- |
| `bootstrap` | Creates a scoped SSH recovery grant and an nftables host-service policy, installs a disposable persistent network fixture ordered after the guard and before full restore, enables the protected socket, validates the systemd units, and establishes an active ready baseline. |
| `stage-guard` | Arms the early barrier and confirms the protected socket and nested-veth host probe are denied while the full restore unit remains active. |
| `verify-ready` | Runs the production restore and readiness checks, then confirms that the barrier is released and the explicitly granted veth probe works. |
| `failure-cases` | Rejects an invalid candidate, corrupt/missing/unsupported persisted state, and a temporarily unavailable nft executable; while nft is still unavailable it verifies the retained barrier and blocked socket, then restores the executable for recovery. It also includes a test-only wrapper that pauses after committing the barrier so the runner can SIGKILL the restore process before an expired journal with an empty prior policy is rolled back. Every injected file/executable is restored in `finally`. |
| `calibrate-probe` | Starts a test-owned local Docker 29 daemon with live-restore, builds a local TCP/UDP echo image without registry access, and temporarily allows only the QEMU hostfwd source so the runner must verify positive `H3-CONTAINER` over TCP and `H3-UDP` over UDP. |
| `restrict-probe` | Re-prepares scoped TCP and UDP published-port grants with their source narrowed to the nested-veth client. Both veth probes must remain positive while the runner verifies both external QEMU hostfwd paths are blocked. |
| `docker-restart` | Restarts the test-owned Docker systemd service with `restart=always` and live-restore without pre-arming the barrier. A test-only `ExecStopPost` assertion requires the production `ExecStop` hook to have installed it before the next start; a four-second start window makes the barrier observable. Both veth probes must fail while it is present, and the same container must answer over TCP and UDP after verified restore. The runner also monitors both external hostfwd paths throughout. |
| `pre-failed-reboot` | Saves the exact valid persisted-policy bytes in the root-owned H3 manifest, verifies the active ready baseline, arms the barrier, then changes only the persisted schema to unsupported value `999` before the host records the boot boundary. |
| `post-failed-reboot` | Waits up to 180 seconds for systemd's boot jobs to settle without starting units, then requires a new boot ID, retained guard, inactive full/Docker restore, inactive protected socket, blocked host and veth probes, and continued access through the runner's fresh SSH connection. It restores and hash-verifies the exact saved bytes, starts production recovery, and requires positive host and TCP/UDP container probes before the valid-reboot phases continue. On failure, it records unit state and the relevant boot journal in the phase output. |
| `pre-reboot` | Saves the policy and arms the barrier before the runner records the old boot ID and reboots the guest. |
| `post-reboot` | Waits up to 180 seconds for systemd's boot jobs to settle without starting units, then requires a new boot ID, successful guard/full-restore/readiness results, the automatically recreated veth and automatically started protected socket, restored host and container TCP/UDP probes, and the same running live-restored container. It does not recreate the veth or start the socket from the SSH phase. The runner continues checking that the now-unapproved external TCP and UDP hostfwd paths stay blocked. On failure, it records unit state and the relevant boot journal in the phase output. |
| `cleanup` | Removes only H3-owned Docker resources, drop-ins, network script/unit, socket/service fixtures, and the owned nftables sentinel; disarms the barrier and policy; restores the exact transaction files present before bootstrap. A modified fixture is retained and reported instead of being deleted. |

The network fixture records its namespace inode and host-veth ifindex/MAC in a root-owned per-boot registry and the persistent test manifest. Later phases reuse matching resources; occupied names without the matching registry cause an error. Initial fixture files are created exclusively without following symlinks, and their recorded content hashes are checked before updates or removal. Cleanup preserves a changed fixture and reports the mismatch. These checks protect the test environment; they are not product firewall ownership evidence.

The H3 sentinel is an inert, uniquely named nftables table used to detect accidental broad flushes during phases in the current boot. It is expected to disappear at reboot and is recreated only after the new boot has passed the systemd restore checks. The test network unit requires the production boot guard and orders its veth setup before full restore; the enabled socket requires both this network fixture and readiness. Its persistent helper refuses to run outside QEMU/KVM or without the root-owned H3 manifest in an authorized test phase. `/etc/nftables.conf` and `/etc/iptables/rules.v6` are fingerprinted before the test and compared after each phase. The local image echoes HTTP over TCP at `18443/tcp` and the fixed `H3-UDP` token over `18444/udp`; the scoped ACL publishes these at guest ports `18482/tcp` and `18483/udp`. The runner forwards those ports to configurable loopback-only host ports (defaults `22464/tcp` and `22465/udp`) and requires positive controls before it treats a lack of responses during transitions as evidence. No registry or external container service is used.

The test-only SIGKILL wrapper is installed over the guest's `nft` executable only for the duration of the fault injection. It delegates the barrier transaction to the original executable and pauses after the kernel commits it; the guest helper then sends SIGKILL to the complete process group. A `finally` block restores the original executable byte-for-byte before checking that the barrier and pending journal survived. The helper explicitly rolls the expired journal back to its empty prior snapshot, verifies that the barrier and readiness failure remain in force, then runs production restore and confirms that it reapplies persisted state before releasing the barrier. A separate reboot deliberately makes the durable schema unsupported and verifies fail-closed startup across a real kernel boot; it stores the known-good file bytes in the test manifest, checks the recovery SSH path from a new host SSH invocation, and restores the exact bytes before the subsequent valid reboot. Both reboot checks run with external TCP and UDP probes throughout the transition. Each attempt records its stage, timestamp, duration and start time. The runner rejects missing transition coverage or a per-protocol start gap above three seconds. TCP requires application bytes because SLIRP can accept a host-side handshake while guest traffic is blocked. This is measured sampling, not proof that arbitrarily short windows cannot occur.

The helper is not proof that a different Docker firewall backend or version combination is compatible. Docker integration coverage for the broader backend matrix remains in `tests/vm/docker.py`; these phases cover the production systemd guard around a real daemon restart and reboot in one pinned guest configuration. Runtime status and logs belong to the corresponding VM runner artifact, not to this test design document.
